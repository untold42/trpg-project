## 五、分层详解

### 5.1 状态层 ✅

#### 决策

- `history` 是真状态（过程），必须持久化。
- 状态在每次 LLM 调用时现拼，且上下文中只出现一次、永远最新。
  理由：状态必然影响叙述（"有一万两却不知道"会写偏），但快照会过期，不能塞进 `history`。
- `history` 只保留纯叙事（user / assistant 正文），状态与工具中间消息都不进 `history`。
- `current.jsonl` 每轮追加：唯一"边玩边做"的更新；一次磁盘 append 成本可忽略，换崩溃安全。
  落盘（每轮，廉价）≠ 蒸馏（存档，昂贵）。
- `世界线程.json` 放在 `游戏数据/` 下，因此被"状态现拼"自动纳入每次调用；宏观时间线不落档，由只读剧本按日期现切。

#### 机制（已实现）

```python
# 每次调用 LLM 都重新拼装，工具循环里也重拼
messages = [
    {"role": "system", "content": 规则},
    {"role": "system", "content": 前情},        # 上一局存档（若有）
    *history,                                    # 纯叙事
    {"role": "system", "content": 当前状态},      # 现拼，只此一份，放末尾
]
```

- 状态块放 messages 末尾（稳定前缀利于上下文缓存）。
- 工具循环里每次 `send_messages` 都重拼状态 → 写最终叙述前看到的一定是刚落地的值。
- 实现：`engine.py` 的 `snapshot_state()` / `GameSession.build_messages()`。
- 上一轮状态 + 当前状态：`engine.state_stack = deque(maxlen=2)`（只两份、不累积）——每轮末
  `append(本轮状态)`，下一轮把栈顶（上一轮）与 `===== 当前状态 =====` 一起发给 LLM；
  探索时时间在流动、玩家在走动，模型自行对比变化，代码不计算差值。

#### 边界规则

- `游戏数据/` 是领域自有存储区：禁止通用文件工具写（`_guard_game_data()`），只能走专用接口 + `state_manager`。
- `file_tools` 默认禁用（`registry._DISABLED`：不下发给 LLM、也不可被调用；代码保留在 `tools/大模型/file_tools.py`，设 `TRPG_FILE_TOOLS=1` 可临时启用）。LLM 的知识入口只剩：提示注入 + 类型化工具。
- 凡进 `游戏数据/` 的文件，必须有类型化接口，否则视为设计漏洞。
- 不是所有 `游戏数据/` 文件都进 LLM 上下文：`snapshot_state()` 排除 `足迹`（探索点）与 `时钟.json`——它们只供前端 `/state`、`/clock` 读；`世界线程` 按「纳入上下文」裁剪后注入，`宏观时间线` 现切窗口注入。
- 并发写保护：`state_manager` 的 `load`/`save` 同一把 RLock 串行化、临时文件名带 pid+线程号、`replace` 失败重试；`clock`/`derived`/`time_flow` 写盘失败只记日志；`/state`、`/clock` 副作用 `_best_effort` 永不 500。

#### 派生上限（承总纲第 5 条）

`属性.json` 是真相源——体力 = 生命值上限，內力 = 精力值上限；`状态.json` 的
`生命上限`/`精力上限` 只是投影。`tools/核心/derived.py` 的 `sync()` 在漂移时以属性为准回写
（上限变小则把当前值夹到上限），由 `engine.snapshot_state()` 与 `time_flow.pump()` 调用
→ 养成提高內力/体力后，上限与睡眠恢复量自动跟上。

"孤儿"（有文件、无写接口）由代码补接口：`属性.json`（`update_ability`/`train_skill`）——未做（见 `TODO.md`）。`游戏存档.md` 已由代码誊写。

### 5.2 记忆层 ✅

#### 两级记忆

```
工作记忆（热）                              长期记忆（冷，chroma）
角色动态档案/活跃/*.md  ──LRU 淘汰条目──►   char_memory（角色/潜意识）
客观事实 ────────────────────────────────►  gm_memory（主持人/客观）
```

- 不对称：主持人记忆只增不淘汰（事实不会遗忘）；角色记忆有容量、会淘汰。
- 淘汰即遗忘，遗忘即潜意识：角色记忆淘汰后进 chroma，需要时被检索回来，以模糊印象形式回到上下文。

#### 两个 collection（已实现）

```
chroma（trpg-db/chroma_db）  访问层：tools/核心/mem_store.py（懒加载）
├─ gm_memory（主持人）
│    客观事实（世界到底发生了什么）
│    metadata: { time, kind? }
│    写：存档时 LLM 蒸馏，只增
│    读：全局，无过滤
│
└─ char_memory（角色）
     主观记忆（记忆/感情/认知）
     metadata: { owner, time, kind? }
     写：存档时，动态档案 LRU 溢出的条目
     读：局内按需，强制 where owner = 当前视角角色
```

- collection 名必须 ASCII（chroma 限制），故用 `gm_memory` / `char_memory`。
- 工具：`DB_query_tool` / `DB_add_and_update_tool` / `DB_query_tool_in_saving`，均按 `collection` 寻址，角色必带 `owner`。id 由代码分配（`_next_id`=max+1），LLM 不编 id。

#### 检索铁律

> 查 `char_memory` 必须带 `owner`；查 `gm_memory` 才全局。跨 owner 检索视为 bug。

这条同时是信息边界机制：`gm_memory` = 客观真相 → GM 主持世界用；
`char_memory[owner]` = 该角色主观认知 → 扮演该角色用；两者之差 = "角色不知道 / 记错了 / 误解了"。

#### 时机

- 局内：允许只读查 chroma（查询轻）。不写任何记忆。
- 存档时（`save_pipeline.run_save`）：
  1. LLM 蒸馏本局 → `gm_memory`（客观）+ 角色动态档案（主观，`update_character_archive`）
  2. 角色档案 §10 情感记忆超 20 条 → LRU 淘汰最旧 → `char_memory`（`tools/大模型/character_archive.py`）
  3. 代码誊写 `游戏存档.md` + 归档
  4. 重置会话（history + current.jsonl）；玩家状态保留（故事连续）

> 注：「动态档案 = 存档时快照」已被世界推演修订——活跃档案随推演每游戏日更新。

#### 旧格式映射（`存档流程.md` 已照此重写）

| 旧 type | 新归属 |
|---|---|
| `event`（客观事实） | `gm_memory` |
| `information`（谁得知/认为/打算什么） | `char_memory`，`owner` = 那个人 |
| `relationship` | 拆两半：客观结盟/敌对→`gm_memory`；A 对 B 的好恶→`char_memory[owner=A]` |

#### 关键规则

- IC / OOC：`梁峰（场外）` 行是玩家对主持人的元对话，不蒸馏。
- id 命名：`gm_N` / `char_N`，两库各自计数。

### 5.3 内容层 ✅

- `trpg-world/` 是正典唯一来源。对 LLM 只以两种方式进入：提示注入 / 类型化检索。
- 规则层全量注入：`主持人/*.md`（小、必须每轮在场）。
- 正典层按需检索：角色静态档案(55)、势力档案、世界设定（大、引用型，全量注入会稀释注意力）——检索接口未做，方案见 §5.8。
- 势力介绍：玩家可见数据独立成文件 `trpg-world/势力介绍.json`（已剔除剧透，人工维护），前端经 `GET /factions`（`tools/服务/factions.py`）读取。前端不再有 `data/` 文件夹——所有游戏数据一律向后端请求。

> 动态 ≠ 把 GM 笔记给玩家看。 `trpg-world/江湖势力/*.md` 含剧透（锦香宫旧为魔教一支、释明暗算唐门等），仍是 GM 正典（真相），只进 LLM、不经接口暴露。

```
trpg-world/江湖势力/*.md    ← GM 正典（真相），只进 LLM
trpg-world/势力介绍.json     ← 玩家可见（已剔除剧透）
        │ tools/服务/factions.py · GET /factions
        ▼
前端画廊 { name, desc, detail, image }
```

#### 角色档案

- `角色静态档案/`（55 个 md，带 `node_type: memory` frontmatter）= 正典。
- `角色动态档案/{活跃,不活跃}/` = 记忆的近端投影；随世界推演每游戏日更新。
- 所有角色地位平等：临时登场而有实质互动的角色一经建档（存档蒸馏时 `update_character_archive` 的 `static`，或 `ensure_static` 兼底），即与预设角色同等对待；不再区分「正典 / 临时」。
- 姓名是唯一主键：每个有实质互动的 NPC 都有独一无二的正式姓名（运行时当场起名，存档兜底）；
  职业/身份代称（「掌柜」「老妇」）只作「原称谓」，不作档案名。`chat` 的 `speaker` / 档案文件名 /
  `char_memory.owner` / `world_sim` 人物线程必须一致。
- 静态与动态档案都不进开局上下文，一律 `get_character(name)` 按需读（见 §5.4）。
- 档案模板（`trpg-world/档案模板/`）：`静态模板.md`（§1–§8，正典）+ `动态模板.md`（§9–§13，近记忆）。现有 55 档待逐步对齐。

### 5.4 引擎层 ✅

#### 结构（已实现）

```
engine.py
  ├─ GameSession       : history + current.jsonl + 开局快照 + 前情
  ├─ TurnRunner.run(input, mode) -> list[Event]
  ├─ TurnRunner.run_save(transcript, rules, hints)   # 存档蒸馏专用回合
  └─ 事件流组装        : 叙事指令 + 工具 UI 事件
save_pipeline.py       : POST /save 的收尾管线
tools/大模型/registry.py      : 工具 schema + 实现的单一真相源
main.py                : bootstrap + 路由
```

- `main.py` 退回纯路由 + bootstrap；不再持有 history、不再写工具循环。

#### 已定 ✅

1. 开局上下文：`规则 + 状态(现拼)`；静态与动态档案都不进开局上下文，改由工具 `get_character(name)` 按需读。
2. "存档"是引擎的特殊命令：`POST /save` 独立收尾管线。
3. 状态块位置：messages 末尾。
4. 回合轮数上限：普通回合与蒸馏回合的工具循环均限 12 轮，防模型无限调工具。
5. 蒸馏看门狗：蒸馏总超时（`SAVE_DISTILL_TIMEOUT`，默认 240s）→ 跳过蒸馏，继续机械存档；`sessions/audit.log` 记录每轮 LLM 耗时 / prompt 大小 / 工具调用。
6. 指令解析的**唯一入口**是 `tools/核心/instructions.py`（`parse` / `try_parse` / `to_text` / `items_of`）：只有「以 `[`/`{` 开头」与「代码围栏块」两条 JSON 路径，否则整段当旁白；**不从散文里抠花括号**（会把模型正在解释的 bug 复读一遍）。规范化（补 `type`、丢空台词）在解析层一次做完。解析结果随轮落盘为 `current.jsonl.instructions`，下游一律读它，不再各自重解析。详见 §17.5。

#### 单一工具注册表（已实现）

- `tools/大模型/registry.py`：`_ENTRIES` 一处定义 `(name, schema, fn)`，派生：
  - `TOOLS = {name: (schema, fn)}`
  - `ALL_TOOLS`（游戏中，排除存档专用 + 禁用）
  - `SAVE_TOOLS`（存档蒸馏白名单，见 §十一）
  - `TOOLS_MAP`（`engine.TurnRunner` 用）
- 新增工具只需在 `_ENTRIES` 加一行，不必再改 `llm.py` / `main.py`。

#### 本局生命周期（已实现）

```
本局进行中 ──┬── 存档 POST /save       → 蒸馏 + 誊写/归档 + reset（状态保留）
             ├── 放弃本轮 POST /abandon → 回滚状态到本局开始 + 丢弃日志 + reset
             └── 中途退出/刷新         → 本局保留；GET /history 续玩
```

- 开局快照：`GameSession` 在本局开始时把 `游戏数据/*.json`（含 `时钟.json`、`世界线程.json`）存到 `sessions/run_start_state.json`；`abandon` 用它回滚。
- `reset`（存档用）保留现状；`abandon`（放弃用）先回滚快照。两者都重拍快照、重读前情、清空 `current.jsonl`。
- `abandon` 在回滚快照前调 `world_worker.clear(wait=True)`，保证在途推演写入也被回滚。
- "重开新档"（清空记忆/状态/前情）暂不做。

#### 存档管线（已实现）

```
POST /save
 1. 代码：current.jsonl ──► 逐字叙事 transcript（按游戏内时间分段）
 2. 代码：统计附加任务（本局进过的建筑 / 两局都出现的无名人）→ hints
 3. LLM ：读《存档流程.md》蒸馏 ──► gm_memory / char_memory / 动态档案 / 见闻 / 建筑结构
          （12 轮上限 + 240s 看门狗；失败/超时则跳过，不阻塞机械存档）
 4. 代码：transcript ──► 游戏数据/游戏存档.md（下一局读作前情）
 5. 代码：归档 ──► 归档存档/<起>~<止> 存档.md
 6. 代码：重置会话（玩家状态保留）
```

- 分工：代码负责机械部分（誊写/归档/重置），LLM 只负责语义蒸馏。
- 修正了原存档流程的 off-by-one（现在蒸馏并归档的是本局）。

### 5.5 表现层 / 事件流 ✅

#### 决策

后端→前端只保留一条契约：有序事件流。事件分两类：

| 类别 | 类型 | 前端行为 |
|---|---|---|
| 叙事指令 | `chat` / `narration` | 线性、点击推进 |
| UI 事件 | `type:"ui"`（`kind`: `bg`/`music`/`minigame`/`mode`/`battle` …） | 旁路；`minigame` 可阻塞叙事 |

- 工具副作用（切背景、放音乐、开小游戏、切模式、开战）通过 UI 事件旁路送到前端——解决工具中间消息被清理后副作用传不出去的问题。
- 历史面板 / 续玩走 `GET /history`（读 `current.jsonl`）；前端不再维护平行的 `historyLog`。
- 元操作走界面按钮：存档、放弃本轮、地图、势力、返回主菜单均不由 LLM 工具触发（确定性 + 二次确认）。
- 模型分工：大模型只产 `chat`/`narration`；`ui_event` 由本地小模型产出。
- 原 `bg` 类型已从 `instruction` 删除。

#### 事件信封（已实现）

工具侧：

```python
from tools.ui_events import ui_event, UI_EVENTS_KEY

def some_tool(...):
    return {"success": True, "message": "...",
            UI_EVENTS_KEY: [ui_event("music", track="市井")]}
```

引擎侧（`engine.TurnRunner`）：取出 `_ui_events` → 收集成流 → 从给 LLM 的结果中剥离 →
返回 `[...UI 事件, ...LLM 叙事指令]`（工具事件在前）。

前端侧：`GameController.sendAction` 拆为叙事（进 `GameScene`）与 UI 事件（走 `handleUiEvents` 旁路）。

#### 输入模式（IC / OOC）（已实现）

`POST /action` 接收 `{input, mode, ke?, 坐标?, 上一坐标?}`：

- `mode:"action"` → 角色行动（IC）。后端组装 `梁峰：<input>` 给大模型。
- `mode:"say"` → 对 NPC 说的话（IC 台词）。后端组装 `梁峰开口说：「<input>」`，让 NPC 回应，不作为行动执行（不得据此跳时间）。
- `mode:"gm"` → 玩家对主持人的场外话（OOC）。后端组装 `玩家的对主持人说的话：<input>`。
- `mode:"continue"` → 「继续」按钮（可选 `ke` 刻数）：`ke=0` 不推进时间、只看更多场景信息；`ke>=1` 推进 N 刻。

`mode` 存进 `current.jsonl`。存档誊写时只改前缀、不改内容：
IC → `梁峰：…` / `梁峰说：「…」`；OOC → `梁峰（场外）：…`（禁止蒸馏）；
旁白 → `GM：…`；NPC 台词 → `GM（人名）：…`。

> 为什么：前缀字符串是脆弱的 UI 约定；"是不是 OOC"必须是数据，不能靠猜。
> OOC 是元对话，不是世界内发生的事，混进 `gm_memory` 会造假事实。

#### 台词 / 场外回合护栏（规则 9 / 12 机械兼底）

`engine.TurnRunner._say_time_guard`：`say`/`gm`/`observe` 模式下——
- 时间：`advance_time` 只允许 ≤ `SAY_MAX_KE=2` 刻；`update_time` / `sleep` 驳回；
- 玩家状态：`modify_money` / `modify_item` / `add_item` / `remove_item` / `modify_hunger` / `modify_hp` / `modify_tp` / `modify_health` / `update_location` / `update_weather` 一律驳回并回错给 LLM（台词≠行动）；
- 放行 `start_battle` / 只读工具；`action` 不受限。

#### 界面布局（已实现）

```
左侧 [菜单] ─► 存档游戏 / 放弃本轮 / 地图 / 势力 / 返回主菜单
右侧（竖排）  数据 / 历史记录 / 行动 / 说话 / 继续 / 主持人
```

- 「数据」弹出金钱/背包/属性/状态（读 `/state`）。
- 「菜单」= `StaggeredMenu`（`closeOnContentClick`）。
- 存档/放弃是界面按钮；`save_game` 工具已退役。

#### 背景 / 音乐（小模型 UI 事件）✅

- `bg` / `music` 均由 UI 事件控制：`{"type":"ui","kind":"bg","data":{position,time}}`、`{"type":"ui","kind":"music","data":{track}}`。
- 前端：收 `kind:"bg"` → `in-game/background.ts`（地点+时辰→图）；收 `kind:"music"` → `in-game/music.ts`（曲库 = `assets/音乐/{固定,动态}/` 下的 mp3，循环播放；固定=界面专用、不走 AI）。
- 背景图规格：严格 1920×1080（16:9）（`assets/背景/<场景>/<白天|黄昏|黑夜>.png`）。展示一律按 16:9：`Background.css` 用 `aspect-ratio:16/9` + `object-fit:cover`。新增背景图必须是 1920×1080（16:9）。

- 已迁移：背景/音乐改由小模型产出（`tools/小模型/ui_sim.py`）：

### 5.6 小模型层

本地小模型：Qwen3-4B（LM Studio，`qwen/qwen3-4b-2507`）。与大模型并列的另一条生成链路。

统一约束（`tools/小模型/small_model.ask_json`）：

- 单次 10s 硬超时：超时 `stream.cancel()` 真中断生成并返回 None，调用方降级（可用 `TRPG_SMALL_TIMEOUT` 覆盖）。`lmstudio.set_sync_api_timeout()` 无效。
- 判定 / 分类类系统提示必须 `/no_think` 且限 `max_tokens`，否则 4B 会陷入长思考。
- 失败一律返回 None（调用方降级，不崩）。

#### 三条管线

| | `ui_event` | 人物表情 | 世界推演 |
|---|---|---|---|
| 时机 | 同步，每轮 | 同步，每轮（有命中才调） | 异步，随游戏日 |
| 延迟敏感 | 高（背景/音乐随场景） | 高（立绘随台词） | 无（off-screen） |
| 输出 | 极小（kind + 字段） | 极小（每行一个枚举） | 两个枚举值 |
| 触发 | 当前叙事 / 场景 | big model 返回的 chat 行 | 推进一个游戏日 |
| 状态 | ✅ 已实现（bg/music） | ✅ 已实现（`expression_sim`） | ✅ 已实现 |

> 人物表情（`tools/小模型/expression_sim.py`）：大模型产 `chat` 不带 expression；引擎在返回前按
> 「整轮上下文 + 每行的表情枚举」让小模型逐行选表情，就地写回 `event["expression"]`。
> 白名单= `CHARACTER_EXPRESSIONS.keys()`（有立绘资源的角色）由代码判定；单候选角色不调模型；
> 失败降级（前端回退 `正常.png` 或不画）。实测 0 越界、可接受命中 ~94%、热调用 ~0.22s。
> 详见 §16.10。

#### 世界推演的核心决策（已实现）

> 小模型只做离散采样，具体叙事交给大模型。

```
每游戏日，对每个活跃人物：
    小模型 ──► { 地点, 事件类型, 纳入上下文 }   ← 都是离散值，幻觉面趋近于零
    代码   ──► 顺利度（加权掷骰，顺+平 ≈ 90%）
        └──► 写入 世界线程.人物线程

玩家遇到该人物时：
    大模型 ──► get_character(name) 读 静态档案 + 动态近记忆
            ──► 自行演绎出既具体、又合正典的叙事
```

为什么只出极少的离散值：4B 生成"具体事实"必然与正典冲突，且会被固化成假事实；
抽象成离散状态后它无从编错。（实测：不逼它极简时，它会把字段写成整段小说、单次 19s+；严格提示后降到 0.5-2s。）

- 事件类型（8 选 1）：营生 / 修行 / 社交 / 赶路 / 生活 / 公务 / 寻医 / 变故
- 顺利度（代码掷骰，5 档）：大顺 5 / 顺 45 / 平 45 / 不顺 4 / 大挫 1
- 地点：自由文本
- 纳入上下文（bool）：按离玩家远近判断是否进大模型视野；不改变推演内容，只决定注入裁剪。

#### 触发与异步（已实现）

```
每次 /action 结束 ──► world_worker.on_turn_end()
    比对「已入队游标」与当前游戏日期
    跨 N 天 ──► 入队 N 个「日任务」（超过 MAX_TICKS=10 则跳过早先的）
                        │  daemon 线程（不阻塞玩家）
                        ▼
   单日：对每个活跃人物采样（是否进上下文由小模型决定）→ 写回世界线程 → 游标推进
         （宏观不在此处理：按当前日期从只读剧本现切窗口）
```

- 入队游标与推演游标分离：避免"没跑完就被重复入队"；进程重启后自动补缺口。
- 世代号 + `clear(wait)`：`clear()` 递增世代，队列里/在途的旧任务出队即作废；`abandon` 在回滚快照前调 `clear(wait=True)`。
- 写入单一化：所有 `世界线程.json` 写入只在 daemon 线程发生，消除写竞争。
- 总开关：`TRPG_WORLD_SIM=0` 关闭。降级：小模型调用失败 → 跳过该人物，不写脏数据。
- 不做代码级「在场豁免」（早期按地点字符串跳过，导致同区域 NPC 线程被永久冻结）——所有活跃人物一律采样，是否进上下文交给小模型。

#### 宏观层（已实现）

- 作者时间线 `trpg-world/世界推演/宏观时间线.json`（89 条，1220-02 ~ 1279-02，覆盖南宋全程，参照史实）。
  每条含 6 字段：`date` / `text`（一句话标题）/ `辐射范围` / `具体影响` / `江湖反应` / `GM叙事参考`——
  后四个是给主持人的叙事素材（地理波及、民生变化、武林反应、可用桥段）。
- 它是唯一真相源：只读、不拷贝、不记「已触发」。注入时由 `tools/核心/macro_timeline.view(今天)` 按当前游戏日现切窗口
  （`date ≤ 今天` = 已发生；`今天 < date ≤ 今天+N月` = 预兆）。因此「放弃本轮」回滚时宏观视图随时钟自动回退，
  无需任何标记；作者改剧本对所有存档立刻生效、小模型不介入（宏观不能编歪）。

#### 存储

```
游戏数据/世界线程.json        ← live（在 游戏数据/ 下 ⇒ 自动进入"状态现拼"与开局快照）
    { 模拟游标,                                   # 世界推演进度（bookkeeping，不注入）
      人物线程: {名: {地点, 最新:{日期,地点,类型,顺利度,纳入上下文}, 流水:[...上限5]}} }
trpg-world/世界推演/宏观时间线.json   ← 只读剧本（不落档；按当前日期现切窗口）
trpg-world/世界推演/推演规则.md
trpg-world/角色动态档案/{活跃,不活跃}/*.md   ← 近记忆文本（大模型读）
chroma                        ← 存档时蒸馏（大模型，重）
```

- 注入裁剪：大模型看到两块——
  - `世界线程`：`world_threads.threads_view()`，只保留 `纳入上下文` 为真的条目，某人物若全被裁掉则不出现；
  - `宏观时间线`：`macro_timeline.view(今天)`，`宏观` = 近 N 月已发生（更早的已在 `gm_memory`）、
    `预兆` = 未来 N 月（仅供铺垫）。N 由 `TRPG_STATE_WINDOW_MONTHS` 调（默认 3）。
  - 存储始终全量，宏观不落档（只读剧本现切）。

#### 大模型如何获知世界

1. `世界线程.json` 及时可见：被「状态现拼」自动纳入每次 LLM 调用；宏观时间线由只读剧本现切。
2. NPC 登场即读档：调工具 `get_character(name)` —— 返回静态正典 + 动态近记忆（活跃优先、退不活跃）。深层记忆（`char_memory[owner]`）不由本工具取——由 LLM 按需再调 `DB_query_tool`。

### 5.7 信息边界（跨层原则）🚧

#### 问题

`history` 是全世界的真相，但一个大模型同时扮 GM 与所有 NPC，会把"梁峰私下做过的事"当成"NPC 也知道"。表现为 NPC 全知 / 上下文泄漏 / 元游戏（实测：出一趟远门回来，NPC 却知道你在外地干了什么）。

#### 原则：可见性是一条跨层统一的轴

| 层 | 隔离键 |
|---|---|
| `char_memory` | `owner` |
| `history` / `current.jsonl` | `在场` / `知悉` / `公开度` |
| `lore` 知识库 | `visibility: public / gm_only / char:<名>` |

#### 关键澄清：`在场` ≠ `知悉`

受害者、被事后告知者、听传闻者都构成知悉。故需三个概念：

| 字段 | 含义 |
|---|---|
| `在场` | 亲眼所见者 |
| `知悉` | 事后被告知/推断得知者 |
| `公开度` | `私密` / `传闻` / `公开` |

NPC X 的知悉集 = `在场∋X` ∪ `知悉∋X` ∪ `公开度≥传闻且能传到 X` ∪ `char_memory[owner=X]`；满足 GM ⊇ 玩家/梁峰 ⊇ 每个 NPC。

#### 已定 ✅：GM 叙述与 NPC 对白拆成两次调用（两段式）

理由：这是唯一能物理隔离知悉集的办法，不依赖提示词自觉（与§5.1"约束必须机械化"同源）。

```
玩家输入
   │
   ├─ Pass 1  GM（客观）  上下文 = 全量规则 + 全量 history + 状态 + 本场在场人
   │           产出 = narration（世界/环境/后果）+ 舞台调度（谁在场、谁开口、立场）
   │           ✗ 不产出 NPC 直接引语
   │
   └─ Pass 2  NPC（主观，每个开口者一次，可并行）
               上下文 = 规则 + 该 NPC 知悉集（过滤后的 history + char_memory[owner]）
                        + Pass 1 给出的"本场事实/自身立场"
               产出 = 该 NPC 的 chat（台词 + 表情）
   │
   ▼
合并：按舞台调度排序 → [narration..., chat...] 事件流
```

- 代价：每轮 N+1 次 LLM 调用（N = 本场开口的 NPC 数）。缓解：只对实际开口的 NPC 调 Pass 2。
- GM 知道全部真相以推动世界，但不得让 NPC 说出其知悉集之外的细节——两者在两段式里天然分离。

#### 待定 ❓

- tag 从哪来：让大模型输出 `{"type":"scene", ...}` 控制事件（便宜但会漏标）；或小模型异步标注（倾向：抽取而非生成，并入 `world_worker`）。
- Pass 2 用哪个模型：复用大模型保人物深度 vs 换更快模型。
- 传播机制：`公开度` 随 `world_sim` 日推演演化（私密→传闻→公开，沿地理/关系网扩散 `知悉`）。
- 校验：重要 NPC 对话事后用小模型核对是否引用知悉集外事实（不阻塞）。
- 数据模型：`current.jsonl` 增加 `在场` / `知悉` / `公开度` / `scene_id`。

### 5.8 知识库层（正典检索投影）🚧

#### 定位：与记忆层性质相反

记忆是"世界发生过什么"（chroma 即真相源）；知识库是"世界本来是什么样"（md 是真相源，chroma 是可重建投影）。

| | 记忆层 | 知识库层 |
|---|---|---|
| 内容 | 本局发生的事实/认知 | 史实/正典/日常参考 |
| 真相源 | chroma 本身 | `trpg-world/考据/*.md` + 正典 |
| 写入者 | 存档蒸馏（LLM） | 构建脚本（代码） |
| 变化 | 每局增长/淘汰 | 稳定，人工维护 |
| 检索过滤 | `owner` | `domain` / `era` / `visibility` |
| 可否进游戏状态 | 可 | 绝对不可 |

#### 已定

- 独立库 `trpg-db/chroma_lore/` + `ingest_lore.py`（与 `init_GM_DB.py --reset` 隔离，互不误清）。
- 单 collection `lore` + metadata 过滤（不拆多库，免 LLM 选库）：`source`（出处）/ `domain`（`daily`/`canon`/`history`/`geography`）/ `era` / `visibility` / `confidence`（`史料`/`二创`/`推测`）。
- chunk 按标题切 + context 前缀，单块 200–500 字；事实卡片，不倒原文。
- 只读工具 `KB_query_tool(query, domain, era, visibility, n)` → 返回带出处的片段；注册进 `registry.py`。
- 触发双轨：LLM 主动调 + 引擎每轮预检索注入（规则层仍全量；正典只走检索）。

#### 铁律 🔒

1. KB 结果永不写入 `gm_memory` / `char_memory`。
2. 注入时标注"这是设定/史实参考，不是本局发生的事"。
3. 无命中 → 明确兜底（"考据未收录，按南宋常识处理"），不允许编造。

#### 与 web search

KB 优先（离线、可溯源、无年代泄漏、无剧透失控）。真接 web search 须独立管线、结果不进 chroma/游戏状态、强制年代过滤；默认不接。

#### 内容源

新建 `trpg-world/考据/`，从《梦粱录》《武林旧事》《蒙元入侵前夜的中国日常生活》等整理事实卡片；先索引现有 `trpg-world/` 正典跑通全链路。

### 5.9 导演（GLM·每局一次）

- 角色：独立于 GM 的「叙事结构」层——把握主线、推进节奏、收束堆积的线索、盯玩家体验。
  动机：GM（DeepSeek）擅长细节却易困于细节，导致主线停滞、疑点越堆越多。
- 模型：GLM（智谱，走 OpenAI 兼容端点，不引入新依赖）。比本地 4B 强、比 DeepSeek 免费，
  但很慢（一次 40–200s）→ 只异步跑、每局一次（一局顶多 ~7 个游戏日，常驻即可）。
- 输入：《故事大纲》（system，`trpg-world/故事大纲.md`，热读）——唯一能看大纲的角色；
  外加上一局逐字存档（`游戏存档.md`）；不给现成的「悬着」清单（实测它自己能找全，还能挖出「主角行动未交代」这类推断线索）。
  首局无前情时退用当前状态/开局设定兜底（否则导演永远不跑，开场也就永远没钩子）。
- ⚠️ 信息分层 · 剧透兼底：大纲含身份/结局底牌，而《导演简报》会进 GM 上下文 →
  提示词黑名单 + 代码兼底双保险：命中底牌词先重试改写，仍命中则机械消弧（`scan_spoilers` / `sanitize`）。
- 存储 / 注入：`游戏数据/导演简报.json` ⇒ 随「状态现拼」每轮注入（常驻上下文）；
  生成中 / 失败 / 空内容时不注入。
- 提示词 v5（实测版）：v4 基础上——接《故事大纲》（system）+ 服务主线但绝不剧透（剧透黑名单 + 不得在「禁止项」点名底牌）；
  强制取舍（1 主线 + ≤2 支线 + 穷尽「冷藏/砍」+ ≤3 禁止项 + ≤2 建议）+ 防漏自查节
  （第八节：自己从正文找所有未回收的线，含主角行动）。
- 测试：`python director_probe.py`（`--e2e` 跑生产路径、`--no-outline` 对照）——首局找钩子 / 有前情考取舍与找漏 / 剧透扫描。
- 降级：429 / 超时 → 保留上一版，永不阻塞。开关 `TRPG_DIRECTOR=0`。
- 环境变量：`GLM_API_KEY`（必需）、`GLM_MODEL`（默认 `glm-4.5-flash`）、`GLM_TIMEOUT`、`GLM_MAX_TOKENS`。
- ⚠️ GLM-4.5-Flash 计划 2026-01-30 下线（之后自动路由 4.7）；模型名做成配置，勿硬编码。
  免费模型 429 是常态（4.7 当前常被限流）；思考模式默认动态开启，`max_tokens` 要给足（思考占额度）。
