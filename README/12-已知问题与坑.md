## 十七、已知问题 / 坑

### 17.1 运行与数据

1. 别用外部工具（DB Browser 等）打开 `chroma_db`：chromadb 的 Rust 内核启动要拿写锁，被占会静默卡死、无任何输出。
2. `游戏数据` 文件的并发写：Flask 多线程下 `open()` 读与 `os.replace` 可能撞 `PermissionError: [WinError 5]`；已修（同锁 + 唯一 tmp + 重试 + 副作用不 500）。别用编辑器/数据库工具开着 `游戏数据/*.json`。
3. 只跑一个后端：开两个 `python main.py` 会抢 5000 端口 / 一个跑旧代码，表现为"改了没生效 / 有的对有的不对"。
4. 重启生效：改 `trpg-server` 的 `*.py` 或前端 `*.ts` 必须重启对应进程；改规则 md / `时间影响.json` 免重启（热读）。
5. 数据目录在 `trpg-server/` 下（`游戏数据` / `天气数据` / `归档存档` 与 `tools/` 同级）。
6. 小模型单次 10s 硬超时；`lmstudio.set_sync_api_timeout()` 不管用。

### 17.2 规则 / 逻辑

7. 时间必须权威：任何"过夜/赶路"叙述必须调 `advance_time`（规则 8；睡觉用 `sleep`）；`engine` 有机械兜底。
8. `history` 无滑动窗口：长局会让每轮携带的 history 变长（推高 token / 首字延迟）；用户称上下文足够大，暂缓（见 `TODO.md`）。
9. 足迹不发 LLM；时钟.json 不发 LLM。
10. `update_time` 语义漂移：环境时间自动流后，护栏须从"推进了没落库"改为"大幅跳时却没落库"（待做）；推进已拆为专用 `advance_time`。
11. 挂机跨多日：`world_sim` 靠 `MAX_TICKS=10` 兜底；失焦暂停是主要防线。
12. `file_tools` 已默认禁用；`游戏数据/` 只能走专用接口。
13. 工具返回类型不统一（str / dict / int / list）——目前都能被 `json.dumps`，新工具需注意。

    完 `历史记录框.png` 再 `setShowHistory(true)`（§16.22⑤）。

### 17.5 大模型输出格式：当前处理与「循环重试」搁置方案

> 背景：模型偶发不按 `chat/narration` JSON 数组输出（实测：一次工具调用之后直接写成散文）。当前已做成不会中断玩法；但「重试到正确」的更强方案评估后搁置（结论见下）。

#### 唯一入口：`tools/核心/instructions.py`

**解析只做一次，把「解析结果」当真相落盘；`assistant_raw` 只留作审计。**

只有两条路，不再是多级瀑布：

```
剥掉围栏后，文本以 `[` 或 `{` 开头  →  按 JSON 解；解不出返回 None（交上层重发修正）
文本里有 ``` 围栏块                →  解第一个围栏块（允许「前言 + 代码块」）
否则                              →  整段当一条 narration
```

`parse(raw)` 永不返回 None；`try_parse(raw)` 只走 JSON 路径，解不出返回 None（供「要不要重发」判断）。规范化在 `normalize()` 里一次做完，下游不再检查：

- `type` 认得出（含 `dialogue`/`say`/`台词`/`旁白` 等变体）就保留；认不出或缺 → **有 `speaker` 当台词，否则当旁白**
- `chat` 没有 `speaker` → 降级成旁白（前端只有 chat 才画立绘，空 speaker 取不到人）
- `content` 为空 → 丢掉
- `chat` 的 `content` 恰好等于 `speaker` → 丢掉（模型偶发拿台词项当「角色名牌」，实测连犯三轮）

#### `_finalize` 的兜底顺序（不变）

1. `try_parse(raw)` 成功 → 用
2. 失败 → 追加「模型坏输出 + `FORMAT_CORRECTION`」重发一次（修正消息不写 history）→ `try_parse` 成功就用
3. 两次都不成 → `salvage_narration`：文本不以 `[`/`{` 开头就整段当一条旁白
4. 两次都空 / 都是坏 JSON → 占位 `（系统：主持人回复格式异常，请再行动一次。）`

#### 落库就是真相

`current.jsonl` 每轮新增 `instructions` 字段 = 最终渲染出去的指令数组（**已规范化、已过天气机械改写、已补表情**）。`assistant_raw` 仍保留原始文本供排查。

下游一律 `instructions.items_of(turn)` 取值，**不再各自重解析**：

| 消费者 | 以前 | 现在 |
|---|---|---|
| `GET /history` 的 `tail`（续玩） | 重解析 raw | 读 `instructions` |
| 历史面板 `history_lines` | 每次重解析全部回合 | 读 `instructions` |
| 存档蒸馏 `save_pipeline` | 两处 `parse_instructions` + **一处裸 `json.loads`（零容错）** | 统一 `items_of` |
| 回喂模型 `session.history` | `normalized_assistant(raw)` | `instructions.to_text(items)`（去掉后端补的 `expression`） |

老存档没有 `instructions` 字段 → `items_of` 回落到 `parse(raw)`，不用洗数据。

#### 踩过的两个坑（别再走回去）

1. **不要从散文里抠花括号。** 模型解释自己格式错误时会在散文里**引用**一段 JSON 当例子。旧实现「截取最外层 `{…}`」把那段引用抠出来当指令——实测一段 217 字的道歉被抠出 47 字，最终输出又变成它正在解释的那句 `苏惜惜：苏惜惜`。
2. **判「像不像 JSON」只看开头。** 旧实现用 `'"type"' in 文本`，于是任何**提到** `"type"` 的散文都失去「当旁白兜底」的资格；上面那段道歉正好提到 `"type"`，既不能当旁白、又只能被抠出那段引用。

代价：模型若在数组前写前言（且没包围栏），现在会走一次重发修正，而不是被就地救回——用「偶尔多重发一次」换掉「偶尔把 bug 复读一遍」。

实测矩阵：

| 情况 | 重试次数 | 结果 |
|---|---|---|
| 合法数组 / 单对象 / 围栏 | 0 | 正常解析 |
| 内层英文引号 | 0 | 转义救回 |
| 散文 → 重试仍散文 | 1 | 当旁白显示 |
| 散文 → 重试成功 | 1 | 用重试结果 |
| 坏 JSON → 重试仍坏 | 1 | 占位提示 |
| 空 → 重试空 | 1 | 占位提示 |
| 散文 → 重试空 | 1 | 用首版当旁白 |
| 坏 JSON → 重试散文 | 1 | 用重试的散文当旁白 |

#### 搁置方案：循环重试直到解析成功

想法：把「重试一次」推广为「循环 N 次直到解析成功，失败的尝试全部丢弃，只保留正确回答」。

评判（为什么先不做）：

- ✅ 可行，且「只保留正确回答」现已成立：失败尝试不进 `history` / `current.jsonl`（日志只存最终 `assistant_raw`）。
- ⚠️ 必须设上限：LLM 随机，无法保证第 N 次合法；不限次 = 死循环 → 回合不返回 → `TurnRunner._lock` 长占 → 整局卡死。建议 2–3 次。
- 🚨 只能重试「最终成文」，绝不重跑工具：若循环包住整个回合，模型可能重复调用 `modify_money` / `advance_time` / `update_location` → 重复扣钱/计时/移动。现有 `_finalize` 天然安全（工具循环只跑一次，重试复用已执行的 `tool_msgs`、且不执行重试里的 tool_calls）——落地时必须保持这个边界。
- 💰 成本线性：每次重试 = 一次带完整 rules+状态+history 的 LLM 调用；3 次 ≈ 4× 延迟与 token。
- 🎯 有效性取决于纠正语：裸重试对「散文漂移」不一定有效；`FORMAT_CORRECTION` 目前只治未转义引号。应按病因分流：纯散文 → 「把同一段内容改写为 JSON 数组，不增删」；坏 JSON → 指出转义问题。
- 🧩 更根本的做法：主请求上 `response_format={"type":"json_object"}`（`llm.complete_json` 已在用）把协议改成顶层对象 `{"instructions":[...]}` —— 从根上保证可解析；代价是与 function calling 通常互斥，需改协议并验证与工具循环共存。

结论：值得做，但只是「1 次 → 2–3 次 + 按病因纠正语」的边际增强，不是银弹；真正保证合法 JSON 要靠结构化输出。当前先维持四层漏斗（已够用），需要时按上述边界在 `engine._finalize` 落地。

### 17.6 本轮新坑（2026-09-26）

1. **后端不重启 = 改了没生效**：本轮大量 `.py`。实测踩过：`engine.py` 22:01 改、后端 21:47 起 → 位置门禁没加载（船到了位置没动）。改 `.py` 后**必须重启，且只跑一个实例**。
2. **位置门禁是启发式**：`_location_guard` / `_location_moved` 靠叙述里的到达词（上岸/下船/靠岸/抵达/渡过/到了[。]/船…贴/埠头…近了…）。GM 用很怪的措辞仍可能漏（有下一轮提醒兜底）。终极解 = 乘船做成独立工具。
3. **追踪必须由前端上报**：`/action` body 不带 `追踪` → `quest_sim` 不跑、真相不注入。追踪真相源在 **localStorage**（`trpg.tracked.quests`）。
4. **任务完成/续接/过期是异步的**：不在 `/action` 响应里，靠 `ui_events` 队列（下次 `/action` 或 `/state`）携回；前端需处理 `kind:"quest"`。
5. **曲牌机制已退役**：`_record_titles` / 注入块已删、`曲牌.json` 不再注入（文件可删）。旧文档（§16.21、交接）里的表述待清。
6. **`知情者` 只存未用**：任务的 `知情者` 已入库，但**未接**「信息边界」（NPC 只能引用自己知道的）。
