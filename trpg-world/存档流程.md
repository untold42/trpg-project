注意你的数据：若对话信息密度高或者十分重要，例如：上官萤说沧帮即日就要解散，原因是xxx，则一句台词便是一条信息。信息示例：上官萤提出解散沧帮，原因是xxx。
反之，若密度低，例如：梁峰在街上闲逛，吃了什么喝了什么，这些一句话概括即可。信息示例：梁峰在扬州吃了xx，闲逛了一会儿。

然后：先调用DB_query_tool_in_saving，把你的数据逐一传入工具，工具会返回每个元素在数据库对应的Top 4。若无意外，你应该得到(n*4)条信息还有他们的memory_id。其中n是你原始数据的条数。接着你应该继续准备一组新的数据，数据元素要么套用pattern1，要么套用pattern2。

pattern1: {
    "operation": "add",
    "id": "新增信息的id",
    "time": "具体时间",
    "data_type": "information"|"event"|"relationship",
    "content": "具体内容"
}

pattern2: {
    "operation": "update",
    "id": "旧的信息的id",
    "time": "新的具体时间",
    "data_type": "information"|"event"|"relationship",
    "content": "新的具体内容"
} 

注意，你应该调用check_DB_length来得知数据库最后一条数据的id。例如，若返回了20，你应该从21开始往下编号。

data_type: event | relationship | information 的选择依据：
1. event是客观事实，意义是规定这个世界到底发生了什么，用于主持人主持游戏。
2. information是知识情报，意义是确立NPC的信息边界，它的结构主要是“谁得知什么/不知道什么”，“谁认为什么”或者“谁打算什么”等等，它的主语一般为某个人。知识情报一般是主观的，可以是虚假的。
3. relationship是人与人，人与组织或者是组织与组织的关系。

同时
event 通常更倾向于 add
information 经常 update
relationship 经常 update

例子如下：
case1:
    {
        "operation": "add",
        "id": "memory_2",
        "time": "1220-01-01卯时",
        "data_type": "information",
        "content": "上官萤认为梁峰来意不善，并打算找机会驱逐他"
    }
case2:
    {
        "operation": "update",
        "id": "memory_5",
        "time": "1220-01-01酉时",
        "data_type": "event",
        "content": "上官隼独自一人回到福州，并联络了点苍派的人"
    }
case3: 
    {
        "operation": "update",
        "id": "memory_10",
        "time": "1220-01-05亥时",
        "data_type": "relationship",
        "content": "梁峰与沧帮和好，称兄道弟"
    }

随即调用DB_add_and_update_tool，进行增加或更新操作。注意：只有新信息与旧 memory 描述的是同一个持续状态、关系、认知、计划，并且新信息使旧状态发生变化、失效或得到补充时，才允许 update。若两条信息可以同时成立，则必须 add。语义相似本身绝不是 update 的依据。
