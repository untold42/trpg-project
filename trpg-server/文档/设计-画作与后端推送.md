# 设计：画作系统 + 后端主动推送（server → GM push）

> 状态：**【✅ 已实现 MVP】**（GM 工具 `commission_painting` 异步生成 + `POST /pending` 轮询 + 画作浮层）。
> 关联：`README/08`（路由/工具/事件）、`README/03 §5.5`（事件流）。
> 缘起：用户想在游戏里「看到 NPC 画的画」；进一步引出**后端主动发起 GM 回合**这一新范式。
> 定位澄清：画作**不必然承载言外之意**，`寓意` 可空；也不做「解读」功能（玩家自己读）。

---

## 〇、一句话

**玩家请人作画 → GM 调一个异步工具（立刻返回「作画中」）→ 图在后台生成 → 画成后由后端主动叫 GM 演一出、把画推到玩家眼前。**

- 画作是**一件作品**：可以有所寄，也可以无所寄——`寓意` **可空**，不逼含义；
  **玩家自己读画，系统不做「解读」功能**。
- 代码侧存 `画面`（客观画了什么）与**可选** `寓意`（若真有寄意），作为 GM 的**常驻台账**（仅 GM 可见）；
  图像只是渲染（图不可控，别拿图当真相源）。

---

## 一、为什么要「后端主动发起 GM 回合」

以往所有回合都由**玩家输入**触发（`POST /action` → `GameRunner.run`）。
但画作是**异步**的：玩家说完「请她作画」就走了，几十秒后图才画好。这时**没人输入**，
却需要 GM 说一句话并把画呈现出来。

→ 于是有了 **push 回合**：后端在异步任务完成时，用 `TurnRunner.run_push(事件文本)`
主动跑一个 GM 回合，结果进推送队列，前端轮询取走。

这打开了后续一批玩法：**拍卖落槌、信使送信、世界事件在玩家静坐时发生**……

## 二、数据流

```
玩家：「请姑娘作画」
  │
  ├─ GM 调工具 commission_painting(作者, 题, 画面, 寓意?, 风格?)
  │     · 立即建记录（状态=作画中）+ 返回 {提示, _ui_events:[art 作画中]}
  │     · 起后台线程（gpt-image-2.5）
  │   GM 本轮叙事：「姑娘铺纸研墨，专心落笔」        ← 不等图
  │
  ├─（这期间玩家追问）build_messages 注入「进行中的画作」→ GM 答「还在画」
  │
  ├─ 后台线程：生成 → 存 trpg-server/画作/<id>.png → 状态=已完成
  │     → runner.run_push("【后台事件】姑娘把画呈上…")   ← 后端主动发起
  │           · 无工具、不推时间、mode="push"
  │           · GM 叙事（**不得描述画的内容/寓意**）
  │     → tools/核心/push.push([art 已完成事件] + GM 叙事)
  │
  └─ 前端每 3s 轮询 GET /pending
        → [art 事件]  → 浮层展示图（对话框正上方、可关、不挡对话）
        → [chat/narration] → 追加进对话（与 /action 同一套渲染）
```

## 三、数据与存储

| 内容 | 位置 | 说明 |
|---|---|---|
| 画作记录 | `游戏数据/画作.json` | `id/作者/题/画面/寓意/风格/状态/图片/创建于/完成于` |
| 图片 | `trpg-server/画作/<id>.png` | 经 `GET /art/<id>.png` 提供给前端 |
| 配置 | `配置/画作.json` | 端点/模型/尺寸/超时/风格后缀/同时在画上限（热改） |

- `寓意` = **仅 GM 与系统可见**的「这幅画真正想说什么」（**可空**：作画未必有言外之意，也可能只是享受艺术）。
  玩家视图（`card`）不含 `画面`/`寓意`——**玩家自己读画**，系统不提供「解读」功能。
- **常驻注入**：`context_view()` 把画作台账（作者/题/画面/寓意/状态/时间，含作画中与已完成）
  每轮注入 GM 上下文（**仅 GM 可见**），让 GM 记得住、前后一致地提。
- 视图：`pending_view()`（作画中，注入 GM 与前端）、`card()`（玩家投影）、`all_view()`（`GET /arts`）。

## 四、新增接口 / 工具 / 事件

| 类型 | 名称 | 说明 |
|---|---|---|
| 工具 | `commission_painting` | GM 委托作画（异步，立即返回「作画中」） |
| 路由 | `GET /pending` | **前端轮询**：`{events:[统一事件流], 作画中:[...]}` |
| 路由 | `GET /art/<id>.png` | 画作图片 |
| 路由 | `GET /arts` | 已完成画作列表（玩家投影） |
| 事件 | `kind:"art"` | `{状态:"作画中"|"已完成", id, 作者, 题, 图片?}` |

## 五、关键决定（与理由）

1. **图不可控，语义层为真**：图像模型画出来和描述常有出入（实测把「空笼」画成「笼中鸟」）。
   所以画作的客观内容（`画面`）由代码存的字段定死；GM 呈现时**只描当下这一刻、不替玩家解读**。
   但**不假定每幅画都有含义**——`寓意` 可以空。
2. **异步 + 推送**：生成 20~70s，绝不能进玩家回合的同步链路。用 `push` 队列 + `/pending` 轮询（不引入 SSE）。
3. **push 回合无工具、不推时间**：防 GM 在「呈现画作」时顺手改状态或跳时。
4. **push 回合跳过「世界变动 / 作画中」注入**（`session.push_mode`）：否则会在画作呈现时把任务到期的世界变动一起演了、还提前 `mark_told`。
5. **并发**：`TurnRunner.run` 与 `run_push` 共用同一把 `RLock` → 玩家回合与 push 回合自动排队，不会同时写 `history` / `current.jsonl`；push 回合**不覆盖 `_last_turn`**（不影响「驳回本轮」）。
6. **存档**：`mode="push"` 的回合，`save_pipeline` 与 `history_lines` 都**不誊写其系统注入的假发言**，只保留 GM 叙事。

## 六、已知边界 / 待做

- **投递是轮询**（3s）：够用但不实时。若日后要「即时」，再上 SSE/WebSocket。
- 目前只做「作画」；**不做「解读」功能**——玩家自己读画。
- 画作页（浏览已完成的画）`GET /arts` 有接口，前端页未做。
- 风格统一走 `配置/画作.json` 的「风格后缀」；「按作者/门派不同画风」未做。
- 图像模型 `size` 参数**不可靠**（会自行定比例）→ 当素材用需自行裁切。
- 其他可复用本原语的玩法：密信 / 通缉令 / 藏宝图 / 画像 / 拍卖落槌。
